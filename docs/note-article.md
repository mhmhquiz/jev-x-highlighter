# X のタイムラインで「興味のあるツイートだけ」を AI で光らせる Chrome 拡張を作った

【画像: 拡張を入れた X のタイムライン。AI・VRC・VALORANT のツイートに色とタグが付いている様子】

## はじめに

X (旧 Twitter) のタイムラインを眺めていると、本当に読みたいツイートが流れの中に埋もれてしまうことがよくあります。

僕が追いかけたいのは、主に次の 3 つです。

- AI (生成 AI、LLM、AI ツールの使い方やニュース)
- VRChat (ワールド、アバター改変、イベント、撮影)
- VALORANT (クリップ、大会、アップデート)

でも実際のタイムラインには雑談やニュース、地震速報、炎上の話題が混ざっていて、スクロールの途中で大事なツイートを見逃してしまいます。

そこで、**タイムラインを普通にスクロールしているだけで、興味のある話題のツイートが自動で色付けされる** Chrome 拡張「Jev X Highlighter」を作りました。

- GitHub: https://github.com/mhmhquiz/jev-x-highlighter

## 何ができるのか

【画像: 強調されたツイートのアップ。右上に「AI · 画像生成」のタグ】

- 興味のあるカテゴリ (AI / VRC / VALORANT など) に当てはまるツイートを、カテゴリの色で強調します。
- 確率が高いほど背景が濃くなり、自信がないときは「?」付きの控えめな強調になります。
- ツイートの右上に「AI · 画像・動画生成」のような小さなタグが出て、どの小分類の話かがひと目でわかります。
- 具体的な情報 (ニュース・手順・コツなど) が多いツイートには 💡 が付きます。
- 逆に、見たくない話題 (地震・炎上・政治など) は「ミュート」として、薄く・折りたたみ・非表示にできます。
- 強調したツイートはサイドパネルの「見逃しリスト」に溜まり、あとからカテゴリ・💡・未読・文字で絞り込んで読み返せます。

【画像: サイドパネルの見逃しリスト】

## キーワード検索ではなく「意味」で判定する

この拡張のいちばんの特徴は、**キーワードではなく、ツイートの意味で判定している**ことです。

キーワードで「AI」を拾おうとすると、次のような困ったことが起きます。

- 「新しいモデルで画像作ってみた」のように、「AI」という語がないのに AI の話をしているツイートを取りこぼす
- 「AIR」「愛」「家電の AI 搭載の広告」のように、関係ないツイートまで拾ってしまう

そこで判定には、TypeSafe AI の **Jev** というモデルを使いました。

Jev は文章を生成する LLM ではなく、「はい / いいえの確率」「選択肢のどれか」「段階評価のスコア」といった**型の決まった判定だけを返す**モデルです。多くの質問に約 100ms で答えられて、入力 100 万トークンあたり $0.042 と非常に安いので、タイムラインのツイートを片っ端から判定する用途にぴったりでした。

カテゴリはキーワードではなく、自然文の説明で定義します。たとえば AI カテゴリはこんな感じです。

```js
{
  name: 'AI',
  instructions:
    'Is this post mainly about artificial intelligence, such as generative AI, LLMs, AI chatbots, AI image/video/music generation, AI tools and how to use them, or AI news and research?',
  criteriaTrue: 'AI の技術・製品・使い方・ニュース・研究・AI で作った作品が話題の中心になっている',
  criteriaFalse: 'AI に一言触れているだけ、または無関係 (例: AIR、愛、家電の「AI搭載」広告、人名のアイ)',
}
```

「該当する例」と「該当しない例」を言葉で書いておくことで、境界線を人間の感覚に近づけています。

1 つのツイートに対して、次の質問を **1 回のリクエストにまとめて**投げています。

- カテゴリごとの「このツイートは○○の話か?」(はい / いいえの確率)
- カテゴリごとの小分類「どの小分類に当たるか?」(選択肢から 1 つ)
- 有益さ「読む人にとって具体的で役立つ情報がどれくらいあるか?」(3 段階のスコア)

Jev は 1 リクエスト内の質問を並列に評価するので、カテゴリや質問を増やしても応答時間はほとんど変わりません。

## 工夫したところ 1: スクロールに「遅れ」を出さない

AI で判定する以上、いちばん気になるのは**遅延**です。ツイートが画面に出てから数百ミリ秒後にパッと色が付くのでは、使っていて気持ちよくありません。

そこで、**ツイートが画面に描画される前に判定を始める**構成にしました。

```
① X がタイムライン API を取得 (約 20 件まとめて)
   └─ fetch / XHR をフックして応答 JSON を横取り
② service worker が Jev に判定を依頼 (約 100ms)
   └─ 結果をツイート ID ごとにキャッシュ
③ ツイートが画面に描画される
   └─ MutationObserver で ID を拾い、キャッシュを引いて即座に色を付ける
```

X はタイムラインの API で約 20 件をまとめて先に取得し、スクロールに合わせて少しずつ描画します。つまり API の応答を受け取った時点で判定を始めれば、2 件目以降のツイートは**画面に入る前に判定が終わっている**わけです。

実装としては、ページ側 (MAIN world) で `window.fetch` と `XMLHttpRequest` をラップし、`/i/api/graphql/` への応答だけをコピーして読んでいます。

```js
const originalFetch = window.fetch;
window.fetch = async function (...args) {
  const res = await originalFetch.apply(this, args);
  const url = typeof args[0] === 'string' ? args[0] : args[0]?.url;
  if (url && TARGET.test(url)) res.clone().json().then(publish, () => {});
  return res;
};
```

`res.clone()` で複製を読むので、X 本体の動作には一切手を加えていません。解析に失敗しても例外を握りつぶして、**X の表示は絶対に壊さない**ことを優先しました。

ほかにも、次のような細かい工夫をしています。

- リツイートは、画面に描画される元ツイートの ID で判定する
- 広告ツイート (`promotedMetadata` を持つもの) は判定しない
- 同じツイートへの同時リクエストは 1 本にまとめ、判定結果はキャッシュして再利用する
- カテゴリの設定を変えたら、設定のハッシュが変わるのでキャッシュが自動で無効になる

## 工夫したところ 2: 精度を「育てられる」ようにした

Jev は追加学習ができないモデルなので、精度を上げるには**質問文と例文を良くしていく**しかありません。

そこで、判定の正誤を記録して改善につなげる仕組みを入れました。

- タグにマウスを乗せると、各カテゴリの確率と 👍 / 👎 ボタンが出る
- 押した結果は「判定ログ」として保存され、設定画面でカテゴリごとの正解率を確認できる
- 間違えたツイートは「例に追加」ボタンで、そのカテゴリの「該当する例 / 該当しない例」に追記できる

【画像: 設定画面の判定ログ。カテゴリごとの正解率と「例に追加」ボタン】

使えば使うほど、自分の感覚に合った判定に近づいていく、という設計です。確率を見ながら、カテゴリごとにしきい値を調整することもできます。

## 工夫したところ 3: 安全と費用への配慮

個人用の拡張とはいえ、API キーや費用の扱いには気を使いました。

- API キーは設定画面で入力して `chrome.storage.local` に保存し、同期もリポジトリへのコミットもしない
- API を呼ぶのは service worker だけで、X のページ側にはキーを渡さない
- Jev に送るのは、判定に必要な情報 (本文・投稿者名・引用・リンクタイトル・画像の代替テキスト・ハッシュタグ) だけ
- 1 日の判定件数に上限 (既定 3000 件) を設け、ポップアップで今日の件数と推定費用を確認できる
- レート制限 (429 / 529) のときは指数バックオフで再試行し、同時リクエスト数も 8 本までに抑える

## 技術構成

- Chrome 拡張 (Manifest V3)
- 素の JavaScript (ビルドなし、依存ライブラリなし)
- 判定: TypeSafe AI の Jev (`POST /v1/systemone`)
- テスト: Node.js 標準のテストランナー (`node --test`)

ファイルは役割ごとに分けています。

- `inject.js`: ページ側で fetch / XHR をフックし、X の API 応答を横取りする
- `x-parser.js`: X の GraphQL 応答からツイートを取り出す
- `content.js`: 描画されたツイートに強調を付ける
- `background.js`: Jev の呼び出し、同時実行数の制御、キャッシュ、利用量の記録
- `jev.js`: Jev へのリクエストの組み立て (PoC スクリプトと共用)
- `options` / `popup` / `sidepanel`: 設定画面、ポップアップ、見逃しリスト

X の画面や API の構造は予告なく変わるので、**API 応答の解析と DOM の操作をそれぞれ 1 ファイルに閉じ込めて**、壊れたときに直す場所がすぐわかるようにしました。

## 進め方: 要件定義と PoC から始めた

いきなり作り始めるのではなく、最初に要件定義書を書きました。

- 目的 (「遅れを感じずに、意味で判定して強調する」)
- 遅れを出さないための構成
- 機能要件と非機能要件 (遅延、API キーの扱い、費用、障害時の動き)
- 最初のバージョンに入れるもの / 後回しにするもの

そのうえで、「Jev は日本語のツイートをどれくらい正しく判定できるか」「1 件ずつ投げるのと、20 件まとめて投げるのではどちらが速くて正確か」を測る PoC スクリプトを用意しました。

開発は 2 段階で進めました。

- フェーズ 1: まず動くこと。カテゴリ判定、強調、表示モード、設定画面
- フェーズ 2: 使い心地。見逃しリスト、小分類、有益さ 💡、ミュート、👍 / 👎 による改善サイクル

「まず動くものを作って、実際に使いながら足りないものを足す」という流れにしたことで、本当に欲しい機能に集中できたと思います。

## 今後やりたいこと

- 興味の度合いを 3 段階以上で出す (「すごく興味あり / 興味あり / 興味なし」)
- 👍 / 👎 の履歴から、カテゴリの説明文の改善案を自動で出す
- 判定結果を IndexedDB に保存して、ブラウザを閉じてもキャッシュを残す

## おわりに

「キーワードではなく意味で判定する」「でも遅れは感じさせない」という 2 つを両立させるために、X の API 応答を先回りして読む構成を考えたのが、このプロジェクトでいちばん面白かったところです。

LLM というと文章を生成する用途が注目されがちですが、Jev のように「判定だけを速く・安く返す」AI を部品として組み込むと、身近な道具をぐっと賢くできることを実感しました。
